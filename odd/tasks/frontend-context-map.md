# frontend-context-map

Objective: every project with the kit keeps an always-on map, history and context of its frontend so an agent finds what to change and reuses before creating; FSD and refactoring happen only on explicit request; a plain help file explains the tool.
Branch: `feat/frontend-context-map` (from `feat/external-design-skills`) · Delivery: single-pr on this branch, work-unit commits; push and PR are the user's decision · Runner: `node --test` (`npm test`), full check `npm run verify` (it rewrites the date in `catalog/explorer.html`; restore that file when nothing else changed).

## Specs

- **S1 — Fast read, nothing missed.** "cuando pido un cambio, por ejemplo, de cambiar los layouts o las cargas, los componentes de carga visuales, quiero que cuando marque esa opción sepa leer rápidamente el frontend y saber qué componentes tiene que cambiar y cómo organizarlo." "crear una especie de archivo con el resumen de todo el frontend para que la IA sepa exactamente que tiene que cambiar y no se deje componentes por cambiar para cuando crezca mucho el depositorio."
  Acceptance: `tools/ui-map.mjs` with no dependencies. `build` writes `ai-frontend-output/ui-map.json` and a short `UI-MAP.md` (components, who uses them, routes, visual role). `impact <role|component>` lists the owner, users, routes, strays and anything unresolved. Unresolved imports are reported, never treated as fine.
- **S2 — Always on, source untouched.** "la parte de, por ejemplo, tener un historial o un contexto, quiero que esto lo implanta siempre, que lo genere siempre en la arquitectura de un proyecto ya hecho." "la filosofía de mantener una separación, un archivo con el historial de todo lo que hay para guiar mejor la ley, eso lo tiene que hacer siempre."
  Acceptance: the installer generates the map and history in every project. It writes only under `ai-frontend-output/`, never moves or renames source, and a scan failure warns without breaking the install. `ui-history.jsonl` records components added or removed between builds. The separation philosophy applies to new code only; existing violations are recorded, not changed.
- **S3 — Check before creating.** "hacer un check de si tengo estos componentes, si voy a crear uno así, etc."
  Acceptance: `ui-map have <name>` answers whether it exists, under which name, how much it is used, and gives catalog candidates when it does not. Guides 04, 06 and 10 use it before searching or creating.
- **S4 — Help file.** "quiero un resumen de esta herramienta que ya tenga de forma estructurada y listo un prompt el cual comentar es decir vale funciona de esta manera puedes hacerlo otro tienes estas herramientas quiero un archivo de explicación y de posibilidades que puedes hacer de manera sencilla y clara"
  Acceptance: `HELP.md` and `HELP.es.md` in the kit: what it is, how it works (always on vs on request), tools, skills per step, what can be asked, ready-to-copy prompts including one to explain it to someone else. The routing block makes a request for a summary of the tool read this file. A test fails if a tool or skill is missing from it.
- **S5 — Component nomenclature.** "la nomenclatura de tipos de componentes que existen y poder tenerlos todos."
  Acceptance: `catalog/component-types.json`, written by the kit: canonical name, aliases, usual layer and catalog category. Names are cross-checked with the Open UI matrix and Component Gallery; descriptions are not copied (Component Gallery shows no license). `ui-map types` shows coverage, unclassified components and possible duplicates by name and alias, stated as a limit. `have` uses aliases.
- **S6 — Context documents.** "un archivo de contexto de los tipos de documentos que tienen que haber, cómo se suele estructurar, en internet cuáles son las mejores combinaciones"
  Acceptance: `guides/13-CONTEXT-DOCS.md` and `ui-map docs`: which documents each profile needs, their structure, and which are missing. `experience/STACK-RECIPES.md`: combinations per project type, each with source, date and evidence level, never labeled best.
- **S7 — Size profiles.** "diferentes modos para cuando el proyecto ya es grande criticar el tiempo o si es algo más pequeño. Es un proyecto más temporal o más rápido de hacer"
  Acceptance: profiles `sprint`, `standard` (default, no install question) and `long-term` set the rigor of `ui-map check` and the required documents. Assumption: "criticar el tiempo" reads as large, long-lived or critical.
- **S8 — History of decisions.** "Que tengan un historial de qué tipos de componentes hay."
  Acceptance: `memory.mjs` also records the component type of a decision, reusing `selections.jsonl`; optional field, old records stay valid. Overlaps `design-flow-guardrails` S2/T4.
- **S9 — FSD only on request.** "esta arquitectura de FSD solo la integre si yo se la pido." "Esta parte de cambiarlo y refactorizar, quiero que sea si él me lo pide explícitamente." "Me gustaría que se pudiese adaptar al tipo de arquitectura o framework que se usa. Sea más como una guía diseño" "no quiero que choquen con los nombres de capas de FSD. Al final quiero que siga esa filosofía."
  Acceptance: `guides/12-ARCHITECTURE.md` with modes `map` (default), `fsd-new`, `fsd-refactor`, including new projects: FSD is never applied unasked. Framework adapters follow official FSD guides (Next.js `_app`/`_pages`, Nuxt and SvelteKit routes under `src/app/routes`, Astro after reading its guide); stacks with no official guide are marked as a kit proposal. `architecture.json` maps existing folders to FSD roles without renaming. Skill `frontend-refactor` follows the official migration guide and runs only on request.
